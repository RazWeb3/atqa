## 3. AI対話記録

全工程の意思決定は AI コーディングエージェントとの対話で行い、成果物はすべてリポジトリに保存されている。

### 3.1 保存されている対話成果物

| フェーズ | 成果物 | 場所 |
|---|---|---|
| ブレスト・UX検討 | UX方向性比較、UXフロー、QA契約、アーキテクチャ案、待機画面設計、配色検討（HTML 7ファイル） | `docs/brainstorm/` |
| 設計仕様 | MVP設計仕様書（要件・データ契約・検査ロジック・異常系・検証条件） | `docs/superpowers/specs/2026-07-27-atqa-mvp-design.md` |
| 実装計画 | タスク分割・依存関係・マイルストーン | `docs/superpowers/plans/2026-07-27-atqa-mvp-implementation.md` |
| 運用・デモ | 運用ガイド、3分デモスクリプト | `docs/operations.md` / `docs/demo-script.md` |

### 3.2 AI と人間の役割分担

| 場面 | AI の役割 | 人間の役割 |
|---|---|---|
| ブレスト | 課題分解、UX方向性の複数案生成 | 方向性の選択（「全文を聞くQA→判断するQA」への転換を採用） |
| 設計 | データ契約・状態遷移・異常系の設計文書化 | 保守的判定（不明なら判定不能、決してpassにしない）等の品質基準の決定 |
| 実装 | コード・テスト・Docker構成の生成 | 実データでの動作確認、実プロバイダでの検証 |
| 修正 | 検出不具合の診断と修正案の生成 | 実測誤読（例: 「一段落」→「ひとだんらく」）に基づく受け入れ判断 |

### 3.3 対話から生まれた代表的な意思決定

1. **三状態判定の採用** — ブレスト時の対話で「AIの不確実性を隠さない」方針を確定し、pass / review / inconclusive の3状態と「不明な場合は決してpassにしない」契約を設計仕様に明文化した。
2. **2段階検査の分離** — 「読み上げ原稿が正しくてもTTSエンジンが誤読する」実測事例（IT→「いっと」）から、原稿の決定的比較（Stage 1）と実音声レビュー（Stage 2）を分離する構成を採用した。
3. **誤検出への対応** — 実行して見つかった誤検出に対し、人手承認型の読みホワイトリスト（7/27 11:55）と未知語の慣用読み判定（同 10:54）を同日中に追加した。
